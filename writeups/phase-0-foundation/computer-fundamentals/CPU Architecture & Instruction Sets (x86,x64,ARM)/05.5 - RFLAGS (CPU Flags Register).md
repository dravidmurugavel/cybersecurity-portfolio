# Introduction

Programs constantly make decisions.

For example:

* Is the password correct?
* Has the file opened successfully?
* Are two values equal?
* Should the program jump to another function?
* Has an arithmetic operation overflowed?

The CPU determines the answers to these questions using the **RFLAGS register**.

Unlike General-Purpose Registers that store data, **RFLAGS stores the outcome of the CPU's most recent arithmetic or comparison operation**. These results influence the next instruction and determine the program's execution path.

During this module, I learned that understanding RFLAGS allows me to predict **why malware chooses one execution path over another**, making it one of the most important registers during reverse engineering.

---

# Why This Matters in Cybersecurity

Many malicious programs contain conditional logic.

Examples include:

* Anti-debugging checks
* Password verification
* License validation
* Sandbox detection
* Virtual machine detection
* Payload activation

These decisions rely on **CPU flags**.

By inspecting RFLAGS, I can understand **why** the malware executed a particular branch instead of simply observing **what** branch it took.

---

# What is RFLAGS?

**RFLAGS** is a special register that stores status information produced by the previous instruction.

Unlike RAX or RCX, it does not store program data.

Instead, it records information such as:

* Was the result zero?
* Was one value greater than another?
* Did an overflow occur?
* Was there a carry during arithmetic?

The CPU immediately uses these flags when executing conditional instructions.

---

# Common CPU Flags

Although RFLAGS contains many bits, several are encountered frequently during malware analysis.

| Flag | Meaning       |
| ---- | ------------- |
| ZF   | Zero Flag     |
| CF   | Carry Flag    |
| SF   | Sign Flag     |
| OF   | Overflow Flag |

Among these, **ZF (Zero Flag)** is the most commonly observed during debugging.

---

# The Zero Flag (ZF)

The Zero Flag becomes:

```text id="rq9kzy"
ZF = 1
```

when the previous operation produces a result of **zero**.

Otherwise:

```text id="x70jlv"
ZF = 0
```

Programs often use ZF to decide whether execution should continue or branch elsewhere.

---

# cmp Instruction

The instruction:

```asm
cmp rax, rbx
```

compares two operands.

It **does not modify either register**.

Instead, it updates the flags stored inside RFLAGS.

Example:

```asm
cmp rax, rbx
je equal
```

If:

```text id="mjlwmu"
RAX = RBX
```

then:

```text id="2ih9cq"
ZF = 1
```

and execution jumps to:

```text id="g76tfh"
equal
```

Otherwise:

```text id="zwhqbh"
ZF = 0
```

and execution continues normally.

---

# test Instruction

Another common instruction is:

```asm
test rax, rax
```

Unlike `cmp`, this instruction is commonly used to check whether a register contains **zero**.

For example:

```asm
test rax, rax
je failed
```

If:

```text id="9b58df"
RAX = 0
```

then:

```text id="jhn87m"
ZF = 1
```

The program jumps to:

```text id="1lx4tk"
failed
```

Otherwise:

```text id="mjlwmz"
ZF = 0
```

Execution continues normally.

During this module, I learned that this pattern appears frequently after functions such as:

* fopen()
* malloc()
* socket()
* connect()

to determine whether the operation succeeded.

# Cybersecurity Perspective

Consider this malware fragment:

```asm
call fopen
test rax, rax
je failed
```

After `fopen()` returns:

* `RAX` contains the return value.
* `test rax, rax` checks whether it is zero.
* RFLAGS is updated.
* `je` decides whether the file opened successfully.

Instead of manually examining the return value, the malware simply relies on the flags stored in RFLAGS.

Understanding this pattern allows me to interpret malware behavior much more quickly.

The malware skips the file because it failed to open it.

Otherwise:

```text id="1v30ti"

```

The malware continues reading the victim's private SSH key.

Understanding RFLAGS allows me to explain **why** the malware chose that execution path.

# Common Misconceptions

### "RFLAGS Stores Program Data"

Incorrect.

General-Purpose Registers store program data.

RFLAGS stores the outcome of the previous operation.

---

### "cmp Changes Register Values"

Incorrect.

`cmp` only updates the flags.

The compared registers remain unchanged.

---

### "`test rax, rax` Compares RAX With Itself"

Not exactly.

Although both operands are the same register, the purpose is to determine **whether RAX equals zero**, updating the flags without changing the register.

---

# Key Takeaways

* RFLAGS stores the results of the previous arithmetic or comparison instruction.
* It does not store ordinary program data.
* `cmp` and `test` commonly update the flags.
* Conditional instructions such as `je` and `jne` rely on these flags.
* Understanding RFLAGS makes malware execution paths much easier to interpret.
* Inspecting RFLAGS is an essential skill during debugging and reverse engineering.
