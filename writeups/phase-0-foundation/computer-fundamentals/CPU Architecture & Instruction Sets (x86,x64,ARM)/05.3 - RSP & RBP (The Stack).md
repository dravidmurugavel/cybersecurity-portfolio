# Introduction

Programs rarely execute a single instruction from start to finish. They constantly call functions, pass arguments, allocate local variables, and return to previous locations. To manage this efficiently, the CPU uses a special memory region called the **stack**.

Two registers play a crucial role in managing this region:

* **RSP (Stack Pointer)**
* **RBP (Base Pointer)**

During this module, I realized that understanding these registers is essential not only for debugging programs but also for understanding how classic attacks such as **stack buffer overflows** work.

---

# Why This Matters in Cybersecurity

During reverse engineering and malware analysis, stack-related registers reveal:

* Current function execution
* Local variables
* Return addresses
* Function arguments
* Stack frames
* Control flow

Many software vulnerabilities also originate from improper stack management.

Understanding RSP and RBP provides the foundation for analyzing memory corruption and exploitation techniques.

---

# What is the Stack?

The **stack** is a region of memory used to store temporary information while a program is running.

It typically contains:

* Function parameters
* Local variables
* Saved registers
* Return addresses

Unlike the heap, the stack is managed automatically by the CPU and operating system.

Whenever a function begins, a new **stack frame** is created.

When the function finishes, the frame is removed automatically.

---

# RSP – Stack Pointer

**RSP** always points to the **top of the stack**.

Every time data is:

* pushed,
* popped,
* or a function is called,

RSP changes.

Example:

```text id="2mdk6l"
RSP

↓

Top of Stack
```

Because program execution constantly pushes and removes data, RSP changes frequently.

---

# RBP – Base Pointer

**RBP** marks the **base of the current stack frame**.

Unlike RSP, it usually remains stable during a function's execution.

This stability allows the CPU and debugger to access local variables and function parameters using fixed offsets.

Think of RBP as a reference point while RSP continuously moves.

---

# Function Calls

Suppose a program executes:

```asm
call process_data
```

The CPU automatically:

* Pushes the return address onto the stack.
* Updates RSP.
* Creates a new stack frame.
* Begins executing `process_data()`.

When the function finishes:

```asm
ret
```

The CPU:

* Reads the saved return address from the stack.
* Loads it into RIP.
* Continues execution after the original `call`.

This entire process happens automatically.

Open GDB:

```bash
gdb sample
```

Display registers:

```gdb

```

Example:


Inspect the stack:

```gdb

```

This displays the values currently stored on the stack, including saved return addresses and local data.

# Cybersecurity Perspective

The stack is one of the first memory regions inspected during malware analysis.

By examining RSP and RBP, I can determine:

* Which function is currently executing.
* How many nested function calls exist.
* Where local variables are stored.
* Where execution will return after the current function.

This provides valuable context while stepping through malware in a debugger.

---

# Stack Buffer Overflow

One of the most well-known software vulnerabilities involves the stack.

Suppose a function allocates:

```c
char buffer[32];
```

If the program copies more than 32 bytes into the buffer without validation, additional data begins overwriting nearby stack values.

Eventually, the attacker may overwrite the:

```text
Return Address
```

When:

```asm
ret
```

executes, RIP loads the modified return address.

Instead of returning to legitimate code, execution jumps to an attacker-controlled location.

This is the foundation of classic **stack buffer overflow attacks**.

---

# Real-World Example

Historically, vulnerabilities involving improper stack management have allowed attackers to execute arbitrary code.

Although modern protections such as:

* ASLR
* Stack Canaries
* NX (DEP)

make exploitation more difficult, understanding stack behavior remains fundamental for vulnerability research and reverse engineering.

# Common Misconceptions

### "RSP and RBP are the Same"

Incorrect.

* **RSP** moves constantly as the stack changes.
* **RBP** usually remains fixed within a function.

---

### "The Stack Stores Every Variable"

Incorrect.

The stack stores temporary data.

Large dynamically allocated objects are typically stored on the heap.

---

### "The Return Address is Stored in RIP"

Incorrect.

RIP holds the instruction currently being executed next.

The return address is temporarily stored on the stack until the `ret` instruction restores it into RIP.

# Key Takeaways

* The stack stores temporary execution data.
* RSP always points to the top of the stack.
* RBP usually marks the base of the current stack frame.
* Function calls automatically push return addresses onto the stack.
* `ret` restores the saved return address into RIP.
* Understanding stack behavior is essential for malware analysis, debugging, and vulnerability research.
